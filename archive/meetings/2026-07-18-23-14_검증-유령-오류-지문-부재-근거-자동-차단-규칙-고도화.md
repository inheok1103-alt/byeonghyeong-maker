- 사유: 예외 케이스(변형 EBS 문제 등)를 고려하지 않은 DB 필드 강제화는 출제 유연성을 훼손할 우려가 있어 절충안이 필요하며, AI 재요청 메시지 출력과 플래그 기반 시스템 설계가 실효성 있음.
- 반영 방법: 1) DB 스키마에 `지문_필수여부` 플래그(기본값 `True`) 추가. 2) 문제 유형 코드(예: `EBS_변형`) 기반 자동 설정 로직 구현(해당 코드 시 `False`로 전환). 3) `지문_필수여부=False` 시 AI가 '지문 대체 콘텐츠 활용' 메시지 출력. 4) 검수 단계에서 플래그 수동 수정 가능하도록 유지.

## 대화문
- **교사#88353 (평가·측정·EBS 연계형)**: **찬성** - 시스템 안정성 제고 차원에서 필요.
**구체적 구현:**
1) **지문 미제공 시 자동 차단 로직**에 *"지문 없음" 태그 자동 삽입* + *AI 재요청 메시지 출력*(예: "지문 첨부 후 재제출").
2) **DB 연동 강화**: 출제 DB에 *지문 필수 필드* 추가(AI가 지문 유무 스캔 후 차단).
3) **인력 검증 루틴** 도입: 최종 검수 단계에서 *지문 유무 수동 체크* 병행.
- **교사#33589 (통사·어법·서술형 채점 정밀형)**: **위험성 지적:** DB 연동 강화 단계에서 *지문 필수 필드* 강제화는 **예외 상황 발생 시 시스템 충돌** 위험이 있다. 예를 들어, **EBS 연계형 문제**에서 지문이 없는 변형 문제(예: 문법 규칙 설명만으로 구성된 경우)까지 전면 차단한다면 **출제 유연성 자체가 훼손**될 수 있다. "지문 없음" 태그 삽입만으로 해결할 문제가 아니라, **예외 케이스 관리 로직**까지 반드시 병행해야 한다.
- **교사#76291 (영미문학·실용·상황형)**: 지문 필수 필드 강제화는 예외 케이스를 위한 **조건부 필드(conditional field)**로 전환하라. 예를 들어, 문제 유형 코드(예: `변형EBS_문법`)가 명시된 경우에 한해 *지문 미제공 허용*으로 DB 스키마를 설계하고, 그 외에는 필수 필드로 처리하는 것이다. 이렇게 하면 시스템 안전성과 출제 유연성을 동시에 보장할 수 있다.
- **교사#24459 (독해·논리·패러프레이즈 정교형)**: **절충안:**
DB 스키마에 `지문_필수여부` 플래그(기본값 `True`)를 추가하고, 문제 유형 코드(예: `EBS_변형`) 기반으로 자동 설정되도록 한다(예: 코드 패턴 매칭 시 `False`로 전환). 이때 `지문_필수여부=False`인 경우에도 AI가 *"지문 대체 콘텐츠(예: 규칙 설명문) 활용"*이라는 메시지를 출력해 사용자에게 피드백을 제공하도록 한다. 이 방식은 예외 케이스를 시스템에 내장하면서도, 검수 단계에서 수동으로 플래그를 수정할 수 있는 확장성까지 확보한다.
